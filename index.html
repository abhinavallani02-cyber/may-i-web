01 · How it works

Three verdicts.
Every call on the record.

Rules live in a YAML file and run in order, before anything reaches the tool. No model, no guesswork.

  • Invisible when it's fine

    An allowed call is forwarded to the server exactly as the agent sent it. The agent never knows may-i is there.

    Only tools/call requests are inspected. Initialization, tool listing, responses, and notifications pass through unmodified, so client and server speak the same stdio protocol they always did.

  • Tool-name globs

    Write read_* once instead of listing every read tool.

    Rules match on the tool name with * as a wildcard. "*" on its own is a catch-all, which makes a good last rule.

  • Argument path prefixes

    Scope any rule to a directory with path_prefix.

    The prefix is checked against the call's path, source, destination, or repo_path argument, comparing whole path segments. The glob and the prefix must both match.

{"jsonrpc":"2.0","id":7,"method":"tools/call",
 "params":{"name":"read_file","arguments":{"path":"src/index.ts"}}}
may-i stderrrule: read_*
[VERDICT] id=7 tool=read_file decision=allow
→ forwarded to the server unchanged

  • Stopped at the proxy

    A denied call never reaches the server. Nothing runs, nothing is touched.

    may-i answers the agent itself. The server never sees the request, so there's no side effect to undo.

  • A clean JSON-RPC error

    The agent gets a well-formed error on the same request id.

    The message names the rule that blocked the call, so the agent can recover and try something else instead of waiting on a request that never returns.

  • Fails closed

    When in doubt, the answer is no.

    Any error, timeout, or malformed response resolves to deny. Calls that match no rule fall back to ask, and an unanswered ask is a deny.

  • Approval where you work

    The call pauses and a human decides.

    If the client supports MCP elicitation, the prompt goes to the client's own UI. If it doesn't, may-i asks at the terminal it's running in.

  • A 30-second window

    Say yes and the call goes through as if it were allowed.

    At the terminal, y forwards the call and a forwards it and remembers the approval for this tool and rule (30 minutes by default, --grant-ttl). n, any other answer, or no answer within 30 seconds denies it.

  • No human, no call

    If nobody is there to answer, the safe default applies.

    With no elicitation support and no controlling terminal, an ask resolves to deny.

  • Append-only JSONL

    Every verdict is appended to the audit log, one JSON object per line.

    allow, deny, ask→approved, ask→denied: all of it lands in audit.jsonl by default, or wherever --audit points.

  • Decisions, not data

    By default a line holds a timestamp, request id, tool name, and verdict.

    Arguments are only recorded if you pass --audit-include-args. Response payloads are never written to the log in either mode.

  • Yours to grep

    Plain text, on your disk.

    No telemetry and no dashboard. Nothing is sent anywhere. Read it with whatever tools you already use.

02 · Architecture

Architecture

Policy as code

One YAML file, checked top to bottom, and the first rule that matches decides. A tool-name glob is checked first, then optional path_prefix and sql.single.

1rules:
2 - tool: read_*
3 action: allow
4 - tool: write_*
5 path_prefix: /etc
6 action: deny
7 - tool: write_*
8 action: ask
9 - tool: "*"
10 action: ask
incomingwrite_file /etc/hosts→ first match wins →DENY
1 · read_*—
2 · write_* /etc—
3 · write_*—
4 · "*"—

A switchboard, not a pipe

JSON-RPC flows both ways over stdio, and each line is dispatched by its shape. A tools/call gets a verdict. A reply whose id matches one of may-i's own prompts is consumed. Everything else passes straight through.

03 · Trust

Built to be trusted

A permission layer only helps if you don't have to trust it blindly.

Local by default

On the default stdio path, nothing leaves the machine. No telemetry, no account, and no network or model in the decision path. With --upstream-url, forwarded tool calls go to the remote server you named, and nothing else leaves the machine.

No model in the path

Your rules decide, not an LLM. Matching is deterministic, and there's no model to run or pay for.

Fails closed

Any error, timeout, or malformed response means deny.

ask timed outDENY
malformed responseDENY
no human to askDENY
unexpected errorDENY

Payloads stay in memory

Inspection is transient. Arguments only reach the disk if you opt in.

04 · Install

Install

Add -- <your server command> and point your MCP client at it.

$npx mayi-mcp

Quickstart

Both configs front @modelcontextprotocol/server-filesystem with the filesystem pack: reads and listing are allowed; writes, edits, moves and creates under /etc or /prod are denied; every other write, edit, move or create asks. Other packs are --rules git|github|postgres, and --policy policy.yaml adds your own rules after the pack.

~/.cursor/mcp.json 
{"mcpServers": {"may-i": {"command": "npx", "args": ["-y", "mayi-mcp", "--rules", "filesystem", "--audit", "/absolute/path/to/audit.jsonl", "--", "npx", "-y", "@modelcontextprotocol/server-filesystem", "/absolute/path/to/project"]}}}

Approval prompts appear in Cursor's own UI (MCP elicitation); this was verified in Cursor. Paths should be absolute.

claude mcp add -s project 
claude mcp add -s project may-i -- npx -y mayi-mcp --rules filesystem --audit /absolute/path/to/audit.jsonl -- npx -y @modelcontextprotocol/server-filesystem /absolute/path/to/project

Writes a project .mcp.json. The nested -- passes through intact. Project-scoped servers need a one-time approval the next time you run claude.

Claude Code's VS Code extension does not show may-i's approval prompt (it auto-declines elicitation, issue #79174), so an ask falls back to a terminal prompt, and resolves to deny when there's no terminal.

05 · FAQ

FAQ

An open-source permission layer for AI agents. It runs as an MCP proxy between your agent and an MCP server, checks every tool call against a YAML policy, and returns allow, deny, or ask. On the default stdio path it loads only Node built-ins and one package, yaml, and its own code is about 1,800 lines across two files, with no framework. The MCP SDK is imported only when you point may-i at a remote server with --upstream-url. npm doesn't install it unless you add it yourself with npm install @modelcontextprotocol/sdk, so a stdio-only install is just may-i and yaml. It's on npm as mayi-mcp under the MIT license.

In order, top to bottom, and the first match wins. The tool-name glob is checked first, with * as a wildcard. Then, optionally, path_prefix compares whole path segments after collapsing .., ., and duplicate slashes, and it follows symlinks. sql.single: select matches exactly one statement. Quotes, -- and /* */ comments, and Postgres dollar quotes are understood, so SELECT 1; DROP TABLE users doesn't match. Compound or unparseable input never matches an allow rule; it falls to a later deny or ask, or to the default ask. It checks only the statement's leading verb, so SELECT … INTO, COPY, or a SELECT calling a function that writes can still match a select rule.

The call asks. may-i is not default-deny and never silently allows: a call that matches no rule goes to the same approval prompt as an ask rule. It is denied only if nobody approves it: a deny answer, no answer within 30 seconds, or no way to ask (no elicitation support and no terminal).

No. may-i only sees calls that go through MCP. Agents with native file tools, such as Claude Code, can read and write files without touching MCP at all. Coverage is strongest on MCP-only tools like databases, APIs, and integrations.

Approval via MCP's native elicitation/create is implemented and verified working in Cursor. Claude Code's VS Code extension declares elicitation support but auto-declines without rendering UI (issue #79174); may-i detects this and falls back to a terminal prompt.

Not yet. The policy loads once at startup, so you need to restart may-i after editing it.

stdio is the default and unchanged: may-i spawns the real server itself. --upstream-url <url> fronts a remote MCP server over streamable HTTP (default), or SSE with --transport sse. It needs the MCP SDK, which isn't installed by default: npm install @modelcontextprotocol/sdk. The client still talks stdio to may-i either way. A static bearer token is supported via --bearer-env <NAME> and is never logged. OAuth is out of scope.

On the default stdio path, no. There's no telemetry, and no network or model in the decision path. With --upstream-url, forwarded tool calls go to the remote server you named, and nothing else leaves the machine. Payloads are inspected in memory and aren't written to disk by default. The audit log records only the decision unless you opt in with --audit-include-args.

Session-scoped grants (--grant-ttl), structural argument matching, rule packs (--rules filesystem|git|github|postgres), and HTTP/SSE upstream have shipped. Richer context in approval prompts is what's next.
